## 1. Strict "1 Class Per `.kt` File" Rule (NON-NEGOTIABLE)

Every `.kt` source file across all core modules (`:common`, `:systemCommon`, `:desktop:common`, `:desktop:nativeCommon`, `:desktop:linuxCommon`, `:mobile:common`), all 8 platform backend modules (`:desktop:windows`, `:desktop:macos`, `:desktop:gtk`, `:desktop:qt`, `:desktop:swing`, `:mobile:android`, `:mobile:ios`, `:web`), all first-party extension modules (`:extensions:alien`, `:extensions:gpu`, `:extensions:imageprocessing`, `:extensions:overlay`, `:extensions:canvas2d`, `:extensions:canvas3d`, `:extensions:media`, `:extensions:mediacontrols`, `:extensions:webview`, `:extensions:codeeditor`, `:extensions:aichat`, `:extensions:threejs`, `:extensions:box2d`, `:extensions:box3d`, `:extensions:dsl`), `:tests`, `:gradle-plugin`, and `:idea-plugin` **MUST export at most ONE public `class`, `interface`, `object`, or `enum class`**.

- **Filename Match**: The filename MUST exactly match the single public type declared inside it (`<TypeName>.kt`).
- **No Bundled Enums or Data Classes**: Never place helper enums, data classes, listener interfaces, or configuration types in the same `.kt` file as another class. Extract every public type into its own dedicated `.kt` file in the appropriate domain subpackage.
- **No Unnecessary Aliases & No Backwards-Compatibility Shims (Zero Alias Hacks)**:
  - Never create redundant alias properties, methods, `typealias` declarations, or duplicate wrapper classes (e.g. adding `isOk` / `ok` alongside `isSuccessful`, `decodeToString` alongside `toString(encoding = "utf8")`, `UdpSocket` alongside `UdpClient`, `Row`/`Col` alongside `ColumnLayout`/`Column`, or duplicate wrapper getters/functions) that clutter and confuse the codebase.
  - Because `GenericUI` is a beta project actively designing its canonical API and layout architecture, **never create or retain backwards-compatibility shims, deprecated wrappers, or legacy class names when refactoring unless explicitly instructed by the user**. Always update all call sites directly to the single canonical API.
- **No Public `*NativeImpl` Exposure (Strict NativeImpl Encapsulation)**: `*NativeImpl` interfaces, classes, properties (`nativeImpl`, `webSocketNativeImpl`, `customNativeImpl`, `nativeImplOverride`, etc.), and methods (`openBodyReadableNativeImpl`, `openStreamNative`, `resolveNativeImpl`, etc.) **MUST NEVER be publicly accessible** on user-facing classes. All `*NativeImpl` references on user-facing components, streams, I/O utilities, databases, network clients, and extensions must be `internal`, `protected`, or `private`.
- **Fail-Fast Runtime Error When a Requested Native Has No `NativeImpl` on the Active Backend**:
  - If any requested component, extension widget, or native capability has no `NativeImpl` on the active backend (or if an extension's backend provider has not been registered, or if a `Window` / `Application` is launched without an active `NativeFactory` or without content), it **MUST throw an immediate runtime exception (`UnsupportedOperationException` or `IllegalStateException`)** instead of silently falling back to a no-op stub or running with no content.
- **`Readable`, `Writable`, & `Stream` Interfaces, `Network` (`openTcpSocket` / `openUdpSocket`), `TcpSocket` & `UdpSocket`, `HttpConnection` (`HttpRequest` & `HttpResponse`), Purpose-Specific `*NativeImpl`s, `ByteBuffer`, `ReadableByteBuffer`, & `WritableByteBuffer` Contract**:
  - `Readable`, `Writable`, and `Stream` (`com.nexustools.genericui.io.Readable`, `com.nexustools.genericui.io.Writable`, and `com.nexustools.genericui.io.Stream`) are **interfaces** (`interface Readable : Disposable`, `interface Writable : Disposable`, `interface Stream : Readable, Writable`) mimicking the Node.js stream API (`suspend fun read(maxBytes: Int): ByteBuffer?`, `fun onData(listener: suspend (ByteBuffer) -> Unit): Readable`, `fun write(buffer: ByteBuffer): Boolean`, `fun onWrite(listener: (ByteBuffer) -> Unit): Writable`, `suspend fun pipe(destination: Writable, ...): Long`) AND providing binary primitive read/write methods (`readByte`, `readUByte`, `readBoolean`, `readShort`, `readUShort`, `readInt`, `readUInt`, `readLong`, `readULong`, `readFloat`, `readDouble` / `writeByte`, `writeUByte`, `writeBoolean`, `writeShort`, `writeUShort`, `writeInt`, `writeUInt`, `writeLong`, `writeULong`, `writeFloat`, `writeDouble`) supporting either endianness (`ByteOrder.LITTLE_ENDIAN` default, `ByteOrder.BIG_ENDIAN`) in the same way as `ByteBuffer`. Because `Readable` and `Writable` support byte-based read/write methods directly, standalone `ByteReader` and `ByteWriter` classes are not used.
  - **`Network`, `TcpSocket : Stream`, & `UdpSocket : Stream`**: `Network` (`com.nexustools.genericui.net.Network`) provides `openTcpSocket(...)` and `openUdpSocket(...)`, and checks `GenericUI.activeFactory?.supportsTcp()`, `supportsUdp()`, and `supportsMulticastUdp()` directly (never instantiating/disposing a socket just to check support, and never checking `BackendTarget` in `:common`; each concrete `<Backend>NativeFactory` returns constant `true` or `false` directly). Because HTTP, WebSocket, and `Database` are always supported on all 8 backends, there are no `supportsHttp()`, `supportsWebSocket()`, or `Database.supports()` methods. On backends that do not support raw TCP/UDP (such as `:web`), `NativeFactory.createTcpSocket()` and `NativeFactory.createUdpSocket()` throw `UnsupportedOperationException` directly. `TcpSocket` (`com.nexustools.genericui.net.TcpSocket`) and `UdpSocket` (`com.nexustools.genericui.net.UdpSocket`) are **interfaces** extending `Stream` (`Readable` + `Writable`), backed by `TcpSocketNativeImpl` (`<Backend>TcpSocketNativeImpl`) and `UdpSocketNativeImpl` (`<Backend>UdpSocketNativeImpl`) on supported backends (never `TcpClient` or `UdpClient`).
  - **`HttpClient`, `HttpConnection`, `HttpRequest : Writable`, & `HttpResponse : Readable`**: `HttpClient` (`com.nexustools.genericui.net.http.HttpClient`) provides `request`, `get`, `post`, `put`, `patch`, `delete`, `head`, and `options` returning an `HttpConnection` (`interface HttpConnection : Stream` in `com.nexustools.genericui.net.http.HttpConnection`) that holds `val request: HttpRequest` (`interface HttpRequest : Writable`) and `val response: HttpResponse` (`interface HttpResponse : Readable`), backed by purpose-specific `HttpConnectionNativeImpl`, `HttpRequestNativeImpl`, and `HttpResponseNativeImpl`.
  - **Purpose-Specific Stream `*NativeImpl`s**: Native stream implementations MUST be specific to their purpose rather than generic `ReadableNativeImpl`/`WritableNativeImpl`: `FileReadableNativeImpl`, `FileWritableNativeImpl` (and per-backend `<Backend>FileReadableNativeImpl` / `<Backend>FileWritableNativeImpl`), `HttpConnectionNativeImpl`, `HttpRequestNativeImpl`, `HttpResponseNativeImpl`, `TcpSocketNativeImpl`, `UdpSocketNativeImpl`, `DatabaseReadableNativeImpl`, `DatabaseWritableNativeImpl`, `ResourceReadableNativeImpl`, `MemoryReadableNativeImpl`, and `MemoryWritableNativeImpl`.
  - `ByteBuffer` (`com.nexustools.genericui.io.ByteBuffer`) supports `fun toString(encoding: String = "utf8"): String` (never `decodeToString`) and indexed read/write for primitive types (`Byte`, `UByte`, `Boolean`, `Short`, `UShort`, `Int`, `UInt`, `Long`, `ULong`, `Float`, `Double`) with either endianness (`ByteOrder.LITTLE_ENDIAN` or `ByteOrder.BIG_ENDIAN`), defaulting to the most common endianness (`ByteOrder.LITTLE_ENDIAN`).
  - `ReadableByteBuffer` (`com.nexustools.genericui.io.ReadableByteBuffer` in `ReadableByteBuffer.kt`) takes a `ByteBuffer`, keeps track of `position`, and implements `Readable` from it (used for `openReadable` on `Resource` / `ResourceID` / `Resources` on binary/preloaded resource backends and `Readable.fromBuffer`).
  - `WritableByteBuffer` (`com.nexustools.genericui.io.WritableByteBuffer` in `WritableByteBuffer.kt`) implements `Writable` with **no index parameters**, appending bytes, strings, and endian-aware primitives (`Byte`, `UByte`, `Boolean`, `Short`, `UShort`, `Int`, `UInt`, `Long`, `ULong`, `Float`, `Double`) to the end and automatically expanding its internal buffer, and converts to `ByteBuffer` (`toByteBuffer()`) or `ByteArray` (`toByteArray()`).
  - **`BinaryJson` (BSON), `BinaryPlist` (`bplist00`), & `PreferenceObjectCodec`**: Accept `Readable` and `Writable` directly as their primary encoding/decoding abstractions (`encode(value, writable: Writable)`, `encodeElement(element, writable: Writable)`, `suspend fun decode(readable: Readable)`, `suspend fun decodeElement(readable: Readable)`, `suspend fun decodeAs(readable: Readable, ...)`), which automatically supports `WritableByteBuffer`, `ReadableByteBuffer`, `FileWritableNativeImpl`, `FileReadableNativeImpl`, `TcpSocket`, `HttpRequest`, `HttpResponse`, `DatabaseWritableNativeImpl`, `DatabaseReadableNativeImpl`, and any custom `Readable` / `Writable`. Buffer/byte-array convenience helpers (`encodeToBuffer`, `encode`) instantiate a `WritableByteBuffer` and pass it to `encode(value, writable)`.

## 2. Core Module Hierarchy, Single-`commonMain` Consumer Architecture, & Domain Subpackages

### A. Core & Shared Backend Module Hierarchy
GenericUI backends and extensions are organized as separate Gradle subprojects along the target hierarchy (while consumer applications use a single `src/commonMain/kotlin` source set with optional target-specific source sets such as `src/androidMain/kotlin` when platform-specific classes like Android `Service`s are needed):
- **`:common`**: 100% platform- and backend-agnostic contracts, components, fragments (`IFragment`, `Fragment`, `FragmentHostFragment`, `FragmentHostSystem`, `@AppFragment`, `@MainAppFragment`, `@AppApplication`), windows (`IWindow`, `TitleCapabilities`), applications (`IApplication`, `FragmentApplication`, `BackendTarget`, `AppTarget`), preferences (`PreferenceStore`), resources (`ResourceID`, `ResourceResolver`), styling, and image APIs.
- **`:systemCommon`**: Shared across all 7 non-Web system targets (`Windows`, `MacOS`, `Gtk`, `Qt`, `Swing`, `Android`, `IOS`), including JVM and native targets.
- **`:desktop:common`**: Shared across all 5 desktop targets (`Windows`, `MacOS`, `Gtk`, `Qt`, `Swing`).
- **`:desktop:nativeCommon`**: Shared across all 4 Kotlin/Native desktop targets (`Windows`, `MacOS`, `Gtk`, `Qt`).
- **`:desktop:linuxCommon`**: Shared between `:desktop:gtk` and `:desktop:qt`.
- **`:mobile:common`**: Shared between `:mobile:android` and `:mobile:ios`.
- **Concrete Backends**: `:desktop:windows`, `:desktop:macos`, `:desktop:gtk`, `:desktop:qt`, `:desktop:swing`, `:mobile:android`, `:mobile:ios`, `:web`.

### B. Annotation-Driven Fragment & Application Discovery, 1:1 Android `AppCompatActivity` Codegen, & `Resource.ResourceID`
1. **`@MainAppFragment`, `@AppFragment`, & `@AppApplication` Discovery**:
   - Consumer projects annotate their fragments in `src/commonMain/kotlin` with `@MainAppFragment(targets = [AppTarget...])` and `@AppFragment`, and optionally annotate a custom `FragmentApplication` subclass with `@AppApplication` (or let the Gradle plugin automatically generate `<FragmentName>Application : FragmentApplication` from the resolved `@MainAppFragment`).
   - Consumer projects configure application metadata, window defaults, and theme in `build.gradle.kts` via `genericui { app { ... } window { ... } theme { ... } backends { all() } }` without writing per-backend `*Main` directories or manual `main()` entry points.
   - `AppTarget` includes all common target scopes (`COMMON`, `SYSTEM_COMMON`, `DESKTOP_COMMON`, `NATIVE_DESKTOP_COMMON`, `LINUX_COMMON`, `MOBILE_COMMON`) and all 8 concrete backend targets (`WINDOWS`, `MACOS`, `GTK`, `QT`, `SWING`, `ANDROID`, `IOS`, `WEB`). The Gradle plugin resolves the most specific `@MainAppFragment` per target (`backend (5) > linuxCommon (4) > nativeDesktopCommon (3) > desktopCommon / mobileCommon (2) > systemCommon (1) > common (0)`) and fails the build if more than one `@MainAppFragment` ties at the highest specificity for any enabled target.
2. **1:1 Generated Android `AppCompatActivity` Classes**:
   - On `:mobile:android`, the Gradle plugin (`GenericUiGenerateAndroidActivitiesTask`) generates a concrete `AppCompatActivity` subclass (`class <FragmentName>Activity : GenericUiFragmentActivity()`, where `GenericUiFragmentActivity` extends `androidx.appcompat.app.AppCompatActivity`) mapped **1:1** to every `@AppFragment` and `@MainAppFragment`, plus the corresponding `<activity>` entries in `AndroidManifest.xml` (with `MAIN`/`LAUNCHER` on the resolved Android `@MainAppFragment`).
3. **`FragmentBundle` Command-Line Arguments on System Targets**:
   - On all system targets, the initial `FragmentBundle` passed to `onCreate(savedState: FragmentBundle?)` contains the process command-line arguments (`KEY_COMMAND_LINE_ARGS = "genericui:command_line_args"`), queryable via `savedState.hasCommandLineArgs()`, `savedState.getCommandLineArgs()`, and `savedState.getCommandLineArgsArray()`.
4. **Android-Style `Resource` / `Resource.ResourceID` System**:
   - The Gradle plugin supports creating and translating Android resource files (`drawable/`, `mipmap/`, `values/strings.xml`, `values/colors.xml`, `values/dimens.xml`, `raw/`, `font/`, `xml/`) in both shared modules and app modules, generating `<package>.Resource` with `Resource.ResourceID` (`com.nexustools.genericui.resources.ResourceID`), which translates to Web URLs on `:web`, embedded `.exe` Win32 `.rc`/`.res` resources on `:desktop:windows`, `R.*` IDs on `:mobile:android`, `NSBundle` resources on `:desktop:macos` & `:mobile:ios`, `GResource`/`QResource` on `:desktop:gtk` & `:desktop:qt`, and JAR classpath resources on `:desktop:swing`.

## 3. Modular Two-Tier Extension Architecture (Project-of-Projects vs. Single Project)

Extensions in GenericUI (`:extensions:{alien,gpu,imageprocessing,overlay,canvas2d,canvas3d,media,mediacontrols,webview,codeeditor,aichat,threejs,box2d,box3d,dsl}`) are structured in one of two ways depending on whether they require platform-specific native/JVM/Web implementations:

### A. Project-of-Projects Extensions (`:extensions:<name>:{common,systemCommon,desktop:common,desktop:nativeCommon,desktop:<backend>,mobile:common,mobile:<backend>,web}`)
Used when an extension requires native C/C++/ObjC (`:desktop:*`, `:mobile:*`), Java/LWJGL (`:desktop:swing`), or Web DOM/WebGL/WebGPU (`:web`) implementations:
1. **`:extensions:gpu`** (`:extensions:gpu:{common,systemCommon,desktop:nativeCommon,desktop:swing,mobile:common,mobile:{android,ios},web}`):
   - Provides unified GPU context, shader, VBlank synchronization (`VBlankWatcher`), and offscreen compute/render management (`GpuDevice`, `GpuOffscreenContext`, `VKContext` primary with SPIR-V & MoltenVK on Apple, `GLContext` fallback with Google ANGLE on Windows).
   - Relied upon by `:extensions:imageprocessing`, `:extensions:canvas3d`, and `:extensions:threejs`.
2. **`:extensions:imageprocessing`** (`:extensions:imageprocessing:{common,systemCommon,web}`):
   - Relies on `:extensions:gpu` + base `:common` Image API. Provides `ImageBuffer2DContext` and offscreen in-memory GPU-accelerated image manipulation (`GpuImageProcessor`, `GpuImageFilterChain`, `GpuImageKernel`, `ImageHistogramResult`).
3. **`:extensions:canvas2d`** (`:extensions:canvas2d:{common,systemCommon,desktop:nativeCommon,desktop:{windows,macos,gtk,qt,swing},mobile:common,mobile:{android,ios},web}` + `:extensions:canvas2d:dsl`):
   - Relies on `:extensions:imageprocessing` and `:extensions:overlay`. Provides `Canvas2D`, `Canvas2DContext`, `Canvas2DExtSurface`, `CurveEditorExt`, `Canvas2DOverlayHost`, and `ScrollCanvas2DOverlayHost` (extending `:common`'s `AbstractCanvas`).
4. **`:extensions:canvas3d`** (`:extensions:canvas3d:{common,systemCommon,desktop:nativeCommon,desktop:{windows,macos,gtk,qt,swing},mobile:common,mobile:{android,ios},web}` + `:extensions:canvas3d:dsl`):
   - Relies on `:extensions:gpu`, `:extensions:canvas2d`, and `:extensions:overlay`. Provides unified `Canvas3D` (`Canvas3DConfig`, `Canvas3DRegistry`, `GLContext` with OpenGL ES 3.0+ & Google ANGLE on Windows, `VKContext` with Vulkan 1.2+, MoltenVK on Apple, & WebGPU on Web), `ScrollCanvas3D`, `Canvas3DOverlayHost`, and `ScrollCanvas3DOverlayHost`.
5. **`:extensions:media`** (`:extensions:media:{common,systemCommon,desktop:nativeCommon,desktop:{windows,macos,gtk,qt,swing},mobile:common,mobile:{android,ios},web}` + `:extensions:media:dsl`):
   - Depends **only** on `:common` and `:extensions:overlay` (zero dependencies on `:extensions:gpu` or `:extensions:canvas2d`). Provides `VideoPlayer` (with `VideoOverlayHost`, `VideoPlayerOverlayBinder`, `attachVideoOverlay`, and uniform codec capability reporting), `AudioPlayer` (`AudioPlayerExt`), `AudioAnalyzer` (`AudioAnalyzerExt`), and `WebVttSrtParser`.
   - `:extensions:media:desktop:nativeCommon` provides shared native `libvlc` bindings (`LibVlcBindings`, `DesktopLibVlcVideoPlayerImpl`, `DesktopLibVlcAudioPlayerImpl`, `DesktopLibVlcAudioAnalyzerImpl`) used by `:extensions:media:desktop:{qt,gtk,windows,macos}`, `:extensions:media:desktop:swing` uses `libvlcj` (`uk.co.caprica:vlcj`), and `:extensions:media:mobile:{android,ios}` & `:extensions:media:web` use native platform media components.
6. **`:extensions:mediacontrols`** (`:extensions:mediacontrols:{common,systemCommon,desktop:nativeCommon,desktop:{windows,macos,gtk,qt,swing},mobile:common,mobile:{android,ios},web}` + `:extensions:mediacontrols:dsl`):
   - Standalone system media controls & hardware keyboard media key hooks extension (`com.nexustools.genericui.ext.mediacontrols`), opted into via `extensions { mediaControls() }`.
   - **Zero Extension Dependencies (`:common` Only)**: Does **not** depend on `:extensions:media`, `:extensions:overlay`, or any other extension so it can be used for any purpose.
   - **System Targets Only — Never Implements an Android `Service` or Mobile Helpers**:
     - **Windows (`:extensions:mediacontrols:desktop:windows`)**: Displays transport buttons (`Previous`, `Play/Pause`, `Next`) directly in the Windows Taskbar hover thumbnail preview via `ITaskbarList3` (`ThumbBarAddButtons` / `ThumbBarUpdateButtons`), updates Windows System Media Transport Controls (SMTC), and hooks `WM_APPCOMMAND` / `VK_MEDIA_*` hardware keyboard media buttons.
     - **macOS (`:extensions:mediacontrols:desktop:macos`)**: Integrates with `MPRemoteCommandCenter` + `MPNowPlayingInfoCenter` (Control Center, Now Playing widget, Touch Bar) and hooks `NSEvent` `NSSystemDefined` (`NX_KEYTYPE_PLAY` / `NEXT` / `PREVIOUS`) keyboard media keys.
     - **Linux (`:extensions:mediacontrols:desktop:{gtk,qt}`), `:extensions:mediacontrols:desktop:swing`, & `:extensions:mediacontrols:web`**: Hooks `XF86Audio*` / multimedia keys, MPRIS, and `navigator.mediaSession`.
     - **Mobile (`:extensions:mediacontrols:mobile:{android,ios}`)**: Lightweight no-op stub (mobile apps manage their own Android `Service` / `MediaSession` in `androidMain`).
7. **`:extensions:webview`** (`:extensions:webview:{common,systemCommon,desktop:common,desktop:nativeCommon,desktop:{windows,macos,gtk,qt,swing},mobile:common,mobile:{android,ios},web}` + `:extensions:webview:dsl`):
   - Dedicated Project-of-Projects `WebView` extension.
   - On **Desktop builds** (`:extensions:webview:desktop:{windows,macos,gtk,qt,swing}`), uses the **Chromium** project (`ChromiumBlinkEngine`) for HTML/CSS layout & rendering coupled with **`NJS`** (`lib/NJS`) with its **AsmJit / SLJIT Native JIT Engine** (`com.nexustools.njs.jit.*`).
   - On **Mobile (`:extensions:webview:mobile:android` `android.webkit.WebView`, `:extensions:webview:mobile:ios` `WKWebView`) and `:extensions:webview:web` (`<iframe>`)**, uses the native platform implementation and **NEVER uses `NJS`**.
8. **`:extensions:alien`** (`:extensions:alien:{common,systemCommon,web}` + `:extensions:alien:dsl`):
   - Self-rendered Bootstrap 5.3 `Canvas2D` UI engine (`AlienFactory`, `AlienContainer`, `AlienFragment`, `AlienScrollFragment`, `AlienFragmentHostFragment`, `UnalienContainer`, `AlienRepaintManager` with dirty update regions) on System targets (`:extensions:alien:systemCommon`), and zero-overhead native DOM pass-through on Web (`:extensions:alien:web`). Relies on `:extensions:canvas2d`.
   - Precompiles `bootstrap.scss` into `AlienPrecompiledBootstrapStyleSheet`, implements `IAlien` (`addStyleSheet` / `removeStyleSheet`, default Bootstrap stylesheet removable via `IAlien.BOOTSTRAP_STYLE_SHEET_ID`, and `insertApplicationStyleSheets: Int = 1` by default or `-1` to disable application stylesheets), uses `<genericui:fragment>` as the canonical custom element tag on `AlienFragment`, `AlienScrollFragment`, and `AlienFragmentHostFragment`, and supports 100% of all `ComponentStyle`, `ComponentBootstrap`, and `PrecompiledStyleSheet` CSS properties and transitions.

### B. Single Multiplatform Project Extensions (`:extensions:<name>` + optional `:extensions:<name>:dsl`)
Used when an extension is implemented in 100% shared KMP code atop `:common` and other extensions:
9. **`:extensions:overlay`** (depends **only** on `:common`; auto-enabled by `media()`, `canvas2d()`, and `canvas3d()`): Shared customizable overlay framework (`OverlayHost`, `OverlayHostBox`, `AbstractOverlay`, `PresetOverlay`, `OverlaySlot`, `OverlayState`, `OverlayActions`, `AutoHideController`, `OverlayInputRouter`, `MobileOverlayPreset`, `WebSystemOverlayPreset`, `OverlayPresetResolver`) plus `:extensions:overlay:dsl`.
10. **`:extensions:codeeditor`** (relies on `:extensions:canvas2d`): Extension-only IDE-style code editor (`IdeCodeEditor`, `CodeLanguage`, `CodeEditorTheme`, `CodeDiagnostic`, `ScssLanguageSupport`) plus `:extensions:codeeditor:dsl`.
11. **`:extensions:aichat`** (relies on `:extensions:codeeditor` $\rightarrow$ `canvas2d`): Reusable AI chat drawer and multi-agent orchestrator (`AiChatContainer`, `AIChatDrawer`, `AIChatAgentOrchestrator`) plus `:extensions:aichat:dsl`.
12. **`:extensions:threejs`** (relies on `:extensions:gpu` + `:extensions:canvas3d`): Three.js-style 3D scene graph (`Scene`, `PerspectiveCamera`, `WebGLRenderer`, `OrbitControls`, `Canvas3D`) plus `:extensions:threejs:dsl`.
13. **`:extensions:box2d`** (relies on `:extensions:canvas2d` + `:extensions:canvas3d` $\rightarrow$ `gpu`): 2D rigid-body physics engine (`World2D`, `Body2D`, `Box2DDebugDrawer`, `Box2DCanvas`) plus `:extensions:box2d:dsl`.
14. **`:extensions:box3d`** (relies on `:extensions:canvas3d` + `:extensions:threejs` $\rightarrow$ `gpu`): 3D rigid-body physics engine (`Box3DWorld`, `Box3DThreeJsBridge`) plus `:extensions:box3d:dsl`.
15. **`:extensions:dsl`** (relies **only** on `:common`): `kotlinx.html`-style component builders and MVC classes (`MvcModel`, `MvcView`, `MvcController`).

## 5. Deferred Upward `NativeImpl` Resolution, Fail-Fast Missing `NativeImpl` Contract, & `LayoutFactory` Architecture

1. **Pure Kotlin Construction**: Calling `val button = Button("Save")` or `val box = VStack()` initializes state in pure common Kotlin (`nativeImpl == null`). It MUST NOT throw an exception if no `Application` or `Window` is active yet.
2. **Upward Factory Discovery**: When `parent.addChild(child)` is invoked, `child` calls `resolveBackendFactoryUpward()`, walking up `parent -> parent.parent -> ... -> RootContainer -> Window -> Application` (with fallback to `NativeBackendRegistry.activeFactory`).
3. **Downward Realization Cascade**: When a detached subtree is attached to a live `Window` or `Fragment`, `realizeNativeTree(factory)` cascades **downward** across the entire subtree in pre-order.
4. **Fail-Fast Runtime Error on Missing `NativeImpl`**:
   - When an `Application` is launched or a `Window` is shown (`isWindowShown == true`), an active `NativeFactory` MUST be present and the window MUST have content (`fragmentContainer`, `contentContainer`, or child components); otherwise it throws an `IllegalStateException`.
   - When any visible component or extension widget is attached to a live `Window`/`Application`, if its requested `NativeImpl` (or extension backend provider in `Canvas2DRegistry`, `Canvas3DRegistry`, `VideoPlayerRegistry`, `AudioPlayerRegistry`, `AudioAnalyzerRegistry`, `WebViewRegistry`, `MediaControlsRegistry`, `AlienImplRegistry`, etc.) is not implemented/registered for the active backend, it **MUST throw an immediate runtime exception (`UnsupportedOperationException` or `IllegalStateException`)** rather than running with a silent stub or empty content.
5. **Shared `Layout<I : LayoutImpl>` Helper System & `LayoutFactory` (`NativeFactory.layoutFactory`)**:
   - **Layouts Are Shared Helper Classes, Not Duplicate Component Hierarchies**: Not all layouts need their own `*NativeImpl` widget class on every backend. Instead, a `Layout<I : LayoutImpl>` is a helper class that coordinates child layout on any host `AbstractContainer`. When both a `Container` variant (`LayoutContainer` subclass such as `ColumnContainer`, `AdaptiveCardContainer`, `HybridColumnContainer`) and a `Fragment` variant (`LayoutFragment` subclass such as `ColumnLayoutFragment`, `CardLayoutFragment`, `HybridColumnFragment`) implement the same layout, both delegate to the **exact same `Layout` helper class** (`val layout = HybridColumnLayout(host = this, ...)`).
   - **`LayoutFactory` Per Backend Group**:
     - **`MobileLayoutFactory` (`:mobile:common` $\rightarrow$ Android & iOS)**: Provides dynamic hybrid `LayoutImpl`s that switch between small-screen phone layouts and large-screen tablet layouts.
     - **`WebLayoutFactory` (`:web` $\rightarrow$ JS & WasmJs)**: Provides dynamic hybrid `LayoutImpl`s for resizable browser viewports, and maps `ColumnLayout` directly to Bootstrap 5 `.row` (plus `.g-*`, `.gx-*`, `.gy-*`, `.row-cols-*`) and `Column` directly to `.col` / `.col-*` / `.col-{sm,md,lg,xl,xxl}-*` / `.offset-*` / `.order-*`.
     - **`DesktopLayoutFactory` (`:desktop:common` $\rightarrow$ Windows, macOS, GTK, Qt, Swing)**: For hybrid layouts (`HybridColumnLayout`, `AdaptiveCardLayout`, `HybridSplitNavigationLayout`, `CollapsibleBottomDockLayout`, `ResponsiveMasterDetailLayout`, `ResponsiveBentoGridLayout`, `AdaptiveNavigationScaffoldLayout`), implements **only** the large-screen layout and enforces `window.setMinWindowSize(...)` on the hosting `IWindow` so the desktop window refuses to shrink small enough to ever require the small-screen layout.

## 6. `TitleBar`, `TitleCapabilities`, & Single-Placement Custom Components

## 7B. `ComponentStyle` (`getStyle()`), `ComponentBootstrap` (`getBootstrap()`), Zero String-Keyed Style APIs, Native Control Rendering & `BootstrapType` Tinting, Unified `ThemeConfig`, & Per-Component `*NativeImpl` / `*RenderUtil` Architecture

3. **Strict `:extensions:dsl` Isolation**:
   - DSL builder functions (`style { ... }`, `bootstrap { ... }`, `important { ... }`) live exclusively in `:extensions:dsl` (`DslStyleAndBootstrapBuilders.kt`) and are **never** part of `:common`.

All agents, subagents, and engineers MUST strictly enforce **Extension Isolation** and **Backend Isolation** across the entire `GenericUI` repository:

1. **Zero Extension Leakage into Core Modules (`:common`, `:systemCommon`, `:desktop`, `:mobile`, `:web`, `:gradle-plugin`)**:
   - `:common`, `:systemCommon`, `:desktop` (`:desktop:common`, `:desktop:nativeCommon`, `:desktop:linuxCommon`, `:desktop:windows`, `:desktop:macos`, `:desktop:gtk`, `:desktop:qt`, `:desktop:swing`), `:mobile` (`:mobile:common`, `:mobile:android`, `:mobile:ios`), and `:web` **MUST NEVER** import, reference, hardcode, or include any classes, tag names, CSS selectors, or logic belonging to any extension (`:extensions:alien`, `:extensions:gpu`, `:extensions:imageprocessing`, `:extensions:overlay`, `:extensions:canvas2d`, `:extensions:canvas3d`, `:extensions:media`, `:extensions:mediacontrols`, `:extensions:webview`, `:extensions:codeeditor`, `:extensions:aichat`, `:extensions:threejs`, `:extensions:box2d`, `:extensions:box3d`, `:extensions:dsl`).
   - For example:
     - **No Alien logic/tags in `:common`, `:systemCommon`, `:desktop`, `:mobile`, or `:web`**: `AlienFragment`, `AlienScrollFragment`, `AlienFragmentHostFragment`, `AlienContainer`, `UnalienContainer`, `AlienImpl`, `AlienBootstrapPainter`, `genericui:alien-container`, and `genericui:unalien-container` belong strictly inside `:extensions:alien` (while all `Fragment` subclasses share the canonical `genericui:fragment` custom element tag).
     - **No VLC/Media or MediaControls logic in `:desktop` or `:common`**: All VLC/media decoding, shaders, and playback pipelines belong strictly inside `:extensions:media`, and all OS media transport / taskbar preview / keyboard media key hooks belong strictly inside `:extensions:mediacontrols`.
     - **No VBlank/GPU or 2D/3D Canvas rendering pipelines in `:common` or core backends**: `VBlankWatcher` lives in `:extensions:gpu`; `ImageBuffer2DContext` lives in `:extensions:imageprocessing`; `Canvas2D` and `Canvas3D` live in `:extensions:canvas2d` and `:extensions:canvas3d`.
2. **Strict Backend Isolation (Zero `BackendTarget` Branching or String Parsing in `:common`)**:
   - `:common` MUST remain 100% platform- and backend-agnostic. Never place platform-specific code, `BackendTarget` branching (`backendTarget != BackendTarget.Web`, `backendTarget == BackendTarget.Android`, `when (backendTarget)`), or string parsing (`BackendTarget.fromBackendName(backendName)`) inside `:common`.
   - Instead, each concrete backend (`<Backend>NativeFactory` / `<Backend>*NativeImpl`) MUST return its `BackendTarget` enum, `TitleCapabilities`, and capability booleans (`supportsTcp()`, `supportsUdp()`, `usesBrowserManagedImageLoading`, etc.) directly as constant values with zero runtime logic, and features that are always supported across all 8 backends (`HTTP`, `WebSocket`, `Database`) must not have redundant `supports*()` methods.
   - Each backend module (`:desktop:windows`, `:desktop:macos`, `:desktop:gtk`, `:desktop:qt`, `:desktop:swing`, `:mobile:android`, `:mobile:ios`, `:web`) MUST remain strictly isolated within its own module and shared parent (`:systemCommon`, `:desktop:common`, `:desktop:nativeCommon`, `:desktop:linuxCommon`, or `:mobile:common`), never referencing or coupling to another sibling backend.
3. **Strict Extension-to-Extension Isolation**:
   - Each extension in `:extensions:<name>` MUST only depend on `:common` and its explicitly declared upstream extension dependencies (e.g., `:extensions:overlay` and `:extensions:mediacontrols` depend **only** on `:common`; `:extensions:media` depends only on `:common` and `:extensions:overlay`; `:extensions:canvas2d` depends on `:extensions:imageprocessing` and `:extensions:overlay`; `:extensions:canvas3d` depends on `:extensions:gpu`, `:extensions:canvas2d`, and `:extensions:overlay`; `:extensions:alien` $\rightarrow$ `:extensions:canvas2d` $\rightarrow$ `:extensions:imageprocessing` $\rightarrow$ `:extensions:gpu`).
   - Within Project-of-Projects extensions, `:extensions:<name>:common` MUST remain 100% platform-agnostic, while platform-specific bridges stay strictly inside their respective target submodules.
4. **Subagent Coordination Rule**:
   - Whenever subagents are spawned to work on `GenericUI`, each subagent MUST be explicitly instructed on and bound by Extension & Backend Isolation, with non-overlapping module/directory scopes so extension logic and backend logic never cross-contaminate.

## 12. No Default Tooltips & Global Pointer Drag Capture (`PointerDragManager`)

1. **Zero Default Tooltips in `GenericUI` (Consumer-Driven Tooltips Only)**:
   - `GenericUI` core components (`:common`), backend renderers (`:desktop:*`, `:mobile:*`, `:web`), and extensions (`:extensions:overlay`, `:extensions:media`, `:extensions:mediacontrols`, `:extensions:aichat`, etc.) MUST NEVER set default or fallback tooltips (such as defaulting `tooltip = name`, `?: impl.getText()`, `"Play"`, `"Close"`, `"Volume"`, or `"Expand / Collapse"`).
   - Tooltips (`tooltipText`) default to `null` and are strictly opt-in by consumer applications. Furthermore, native renderers must never display a tooltip that merely duplicates the control's visible text label.
2. **Global Pointer Drag Capture System (`PointerDragManager` & `PointerDragSession`)**:
   - Interactive draggable controls (`SeekBar`, `TrackSeekBar`, `SliderSeekBar`, `ExpandingVolumeSlider`, etc.) use `AbstractComponent.startPointerDrag(...)` backed by `PointerDragManager` (`com.nexustools.genericui.event.PointerDragManager`) and backend window-level pointer capture (`Win32NativeWindowHost` `SetCapture` / `HitRegion.onRelease` and `WebBrowserDomBridge` `window` `pointermove`/`pointerup`/`mousemove`/`mouseup` listeners).
   - Once a drag starts on a knob or track, pointer movement continues updating the drag when the cursor leaves the boundary of the element, and `pointerup` / `mouseup` outside the boundary of the element reliably ends and commits the drag session without auto-hiding active media overlays mid-drag.

## 13. Dual-Thread UI Rendering/Updating vs. Logic/Event-Handler Thread Separation (`GenericUiThreading`)

1. **Strict Separation of UI Thread vs. Logic Thread Across All 7 Non-Web Backends**:
   - On all 7 non-Web backends (`:desktop:windows`, `:desktop:macos`, `:desktop:gtk`, `:desktop:qt`, `:desktop:swing`, `:mobile:android`, `:mobile:ios`), `GenericUiThreading.isSplitThreadingEnabled` is `true` (and `false` on `:web`, where the browser event loop executes both directly):
     - **UI Thread (`GenericUiThreading.uiDispatcher` / `GenericUiThreading.runOnUi` / `GenericUiThreading.runOnUiSync`)**: Exclusively performs native widget mutations, layout passes, style application, and rendering (`Win32` message loop on `:desktop:windows`, AppKit main queue on `:desktop:macos`, GLib/GTK main context on `:desktop:gtk`, `QApplication` main thread on `:desktop:qt`, AWT Event Dispatch Thread on `:desktop:swing`, Android Main `Looper` on `:mobile:android`, and UIKit main queue on `:mobile:ios`).
     - **Logic Thread (`GenericUiThreading.logicDispatcher` / `GenericUiThreading.logicScope` / `GenericUiThreading.runOnLogic` / `GenericUiThreading.runOnLogicAsync`)**: Executes all user event callbacks (`onClick`, `onDoubleClick`, `onContextMenu`, `onPointer*`, `onWheel`, `onKeyDown`, `onKeyUp`), `UiTimerScheduler` callbacks (`setTimeout`, `setInterval`), and application business logic with `GenericUiThreading.isOnLogicThread() == true` and `GenericUiThreading.isOnUiThread() == false`.
   - When component properties or `GenericUiThreading.runOnUi { ... }` are invoked from inside a Logic Thread callback, native widget mutations are enqueued onto the UI task queue and drained on the UI Thread (`isOnUiThread() == true`, `isOnLogicThread() == false`).
2. **Per-Backend `UiThreadDispatcherNativeImpl` Implementations**:
   - `NativeFactory.createUiThreadDispatcher()` provides the backend's `UiThreadDispatcherNativeImpl` (`WindowsUiThreadDispatcherNativeImpl`, `MacosUiThreadDispatcherNativeImpl`, `GtkUiThreadDispatcherNativeImpl`, `QtUiThreadDispatcherNativeImpl` extending `DesktopNativeUiThreadDispatcherImpl`; `SwingUiThreadDispatcherNativeImpl`; `AndroidUiThreadDispatcherNativeImpl`; `IosUiThreadDispatcherNativeImpl`; and `WebUiThreadDispatcherNativeImpl` with `isSplitThreadingEnabled = false`).
   - `:common` never branches on `BackendTarget` to determine threading behavior; each concrete backend's `UiThreadDispatcherNativeImpl` defines `isSplitThreadingEnabled` as a constant boolean.

## 14. Chromium/Chrome Multi-Process Desktop `WebView` Architecture & Helper Executable (`:extensions:webview`)

1. **Chrome-Style Multi-Process Isolation on Desktop (`:extensions:webview:desktop:*`)**:
   - On all 5 desktop backends (`:desktop:windows`, `:desktop:macos`, `:desktop:gtk`, `:desktop:qt`, `:desktop:swing`), `:extensions:webview` runs a Chromium/Chrome multi-process architecture (`ChromiumMultiProcessCoordinator`, `ChromiumProcessType`, `ChromiumHelperProcessConfig`, `ChromiumIpcChannel`, `ChromiumSubprocessLauncher`, `ChromiumSharedMemorySurface`):
     - **`BROWSER` Process**: Runs inside the host GenericUI application process and coordinates navigation, IPC channels, permissions, and composited frame presentation.
     - **`RENDERER` Process**: Isolated per-site/per-tab helper process running `ChromiumBlinkEngine` layout/DOM/paint + `NJS` (`lib/NJS`) JavaScript execution, rendering into a shared-memory surface (`ChromiumSharedMemorySurface`).
     - **`GPU` Process**: Dedicated GPU compositing and rasterization helper process.
     - **`NETWORK` & `UTILITY` Processes**: Isolated network service and sandboxed utility subprocesses.
2. **Dedicated Helper Executable (`genericui-webview-helper`)**:
   - When `extensions { webView() }` is enabled in a consumer project's `build.gradle.kts`, the GenericUI Gradle plugin (`GenericUiPackageTask` / `WebViewHelperBundler`) compiles and bundles the standalone `genericui-webview-helper` (`.exe` on Windows, helper binary inside `.app/Contents/Frameworks` on macOS, sibling executable on Linux/Swing) alongside the application distribution.
   - Mobile (`:mobile:android`, `:mobile:ios`) and `:web` use native platform `WebView` / `WKWebView` / `<iframe>` implementations and never bundle `genericui-webview-helper` or `NJS`.

## 15. Static Core Libraries vs. Packaged Extension Libraries & Executables (`:gradle-plugin`)

1. **Statically Linked Core & Backend Libraries**:
   - Core modules (`:common`, `:systemCommon`, `:desktop:*`, `:mobile:*`, `:web`) and their core image/platform libraries (`libjpeg`/`libjpeg-turbo`, `libpng`, `libwebp`, OS system toolkits) are linked directly into the main application binary/archive.
2. **Modular Dynamic Libraries & Helper Executables for Opt-In Extensions**:
   - Native runtime libraries and helper executables required by opt-in extensions (`libvlc` / `libvlccore` and VLC `plugins/` for `:extensions:media`, ANGLE `libEGL` / `libGLESv2` and MoltenVK `libMoltenVK` for `:extensions:gpu` / `:extensions:canvas3d`, and `genericui-webview-helper` + Chromium/NJS libraries for `:extensions:webview`) are packaged into the application distribution (`GenericUiPackageTask` / `ExtensionNativePackagingManifest`) **strictly when the corresponding extension is enabled** in `genericui { extensions { ... } }`.
